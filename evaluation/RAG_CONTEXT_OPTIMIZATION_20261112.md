# RAG 上下文与纠错路径优化记录

- 开始日期：2026-11-12；在线结果与记录收尾：2026-11-13。文件和实验目录沿用开始日期。
- 目标：处理旧五题配对实验中 RAG 开启后工具循环过长、上下文重复和超时的问题；保留原来的失败成绩，不以减少测试或放宽审核换取成功。
- 当前状态：离线检查与十次真实在线任务、独立计分、Trace/清理核对均完成；工程缺陷已修正，仍没有测得 RAG 修复成功率收益。

## 已定位的问题与修改

旧五题 RAG Trace 中有四个任务出现补丁输出校验失败，共五次拒绝；校验失败后仍执行了 26 次工具调用。其中有三个任务的模型候选已包含适用性判断，但 diagnosis 缺少对应的 `[case_id@revision]` 引用；另一个任务还出现空补丁/不完整结构。旧程序将最终 JSON 的纠错重新送回完整 ReAct 工具循环，丢失了上一轮候选与工具观察，使模型可能再次读取、检索、应用补丁、运行测试。

`repair_workflow.py` 现在为结构化纠错保留上一轮候选和工具观察，使用没有工具权限的模型调用修正校验错误。案例引用、匹配条件、冲突/未知项及补丁字段仍按原契约校验；纠错次数没有增加。无效输出在达到原上限后仍停止。最终候选仍由固定节点重新应用、运行测试并独立审查。

成功案例、拒绝经验及模型主动检索得到的历史案例统一做字段投影。正文档案仍保存在任务状态/Trace，只向模型发送有长度限制的报告、诊断、补丁片段、适用条件、拒绝原因及简短来源。所有初始召回案例继续参与适用性判断，没有通过只保留有利案例改善成绩。提示词增加引用格式示例，并说明已有充分证据时可以直接输出候选，测试已通过且没有新疑点时不必重复调用工具。

## 离线证据

新增三项回归在保存的旧实现上运行得到 `3 failed, 2 deselected`；修正后的上下文测试为 `5 passed`。RAG、上下文、工具和工作流组合为 `76 passed, 16 subtests passed`；最终上下文与评测器组合为 `21 passed`。这些范围有重叠，不相加为独立测试数。模型响应在这些单元测试中被替换，不算真实修复效果。

运行 `python -m evaluation.audit_rag_context --input work/evaluation/rag-ab-five-20261112-budget80k-retry --output evaluation/rag-context-audit-20261112.json`，离线读取旧 Trace，没有调用模型或 Embedding：

- 五题初始 25 条案例上下文为 19,091→19,091 UTF-8 字节；这些短案例没有触发新长度上限，因此不能声称初始上下文缩小。
- 六次动态检索返回的案例由 29,946→22,817 字节，减少约 23.8%。
- 首次输出校验失败后旧模型调用累计约 153.982 秒，仅是旧运行的观测；新纠错也需要一次或多次模型响应，不能将旧时间全部计为节省。

## 在线复测协议

用户将本轮改为在线评测，并给出独立的最多 500,000 Token 额度。使用原五题 `case-03,11,12,19,30`，两组各一次，随机调度、并发 2；同一冻结程序、模型、数据、历史语料与 Docker 镜像，每题 45,000 Token、120 秒、10 次修复尝试。语料构建上限 10,000 Token，十个任务的额度合计 450,000，保守预留总额 460,000 Token。

`--task-tokens` 在 prepare 时登记，worker 从冻结清单读取；运行后不调整预算。评测请求发生用量未知的超时/瞬时故障时停止该任务，保留该题完整额度，不自动重试；两组使用相同规则。Token 输入量仍是近似估算，实际账单只由供应商确定，用量缺失必须明确报告。模型和 Embedding 费率未配置，费用未知。

旧实验每题 80,000 Token，本轮是 45,000；用量未知处理规则也发生变化，因此新旧实验不是单一代码因素的严格因果对照。新实验内部的 RAG 开关对照保持相同预算和策略。五题已经用于定位和调优，只能算开发诊断，不能描述成新的独立盲测或生产基准。

冻结与原始证据目录：`work/evaluation/rag-ab-context-20261112-45k/`；程序快照为同名 `-runtime/` 目录。没有复制 `.env`，没有自动接受补丁或发布到知识库。

## 在线结果

真实模型仍为 `deepseek-v4.1-flash-1017`，Embedding 为 `Qwen/Qwen3-VL-Embedding-8B`，真实 Docker 参与执行与独立计分。

| 指标 | 关闭 RAG | 开启 RAG |
| --- | ---: | ---: |
| 完整成功：reviewable 且六条独立测试通过 | 1/5 | 1/5 |
| 最后候选的六条独立测试通过 | 4/5 | 4/5 |
| 实际执行独立候选测试的任务 | 4/5 | 4/5 |
| 已观测 Token，含任务内 Embedding | 119,460 | 149,924 |
| 用量完整 | 否，三题不完整 | 是 |
| 平均总耗时，含清理 | 113.47 秒 | 121.77 秒 |
| P95 总耗时，含清理 | 127.80 秒 | 124.61 秒 |
| 工具模型完整响应轮数 | 19 | 16 |
| 工具调用数，含被拒绝调用 | 14 | 13 |

配对为关闭组独赢 1、RAG 独赢 1、共同成功 0、共同失败 3；增量为 0，精确 McNemar 双侧 p=1。关闭组 `case-19` 成功，开启组 `case-11` 成功；reviewable 仍表示等待人工审核，没有接受补丁或写入正式知识库。

关闭组 `case-12` 因无效 unified diff 被拒绝应用；另外三题在验证阶段超时。RAG 组四题耗尽时间：`case-03/12/19` 已有最终候选且事后独立测试通过，但未完成工作流；`case-30` 没有最终候选。两组各四份有效候选实际运行了三条既有和三条隐藏测试，总共 48 条独立测试通过；另两题没有执行独立候选测试，不能说全部十题通过。

在线三次 JSON 纠错均使用无工具调用，校验拒绝后额外工具调用数为 0，证明新纠错路径生效。旧 RAG 五题有 36 次工具模型完整响应、39 次工具调用，本轮为 16 次与 13 次；本轮另有三次普通模型纠错调用，不能将它们忽略为零开销。旧轮和本轮预算、未知用量策略及服务时序不同，这些数字只作描述，不能归因成确定的优化幅度。

当前主要瓶颈是总时限：本轮基线复现约需 43.1–75.4 秒；RAG 上下文收集约需 6.0–7.6 秒；RAG 补丁阶段约需 21.2–56.8 秒，随后还需独立验证与模型审查。120 秒往往不足以完成全部步骤。本轮没有移除验证、跳过审查或临时延长任务预算；总墙钟还包含超时处理与清理，不能将 120 秒表述成严格的端到端上限。

两组任务观察到 269,384 Token，语料构建另用 1,771，共 271,155。关闭组三题用量不完整，按每题完整 45,000 Token 额度预留，已知用量加未知任务全额预留与语料用量合计为 328,298；注册时的整体预留为 460,000，均在本轮 500,000 额度内。这是基于项目近似输入预检的预算记录，不是供应商账单，未知用量不能按零计算。RAG 组任务内 Embedding 为 3,882 Token，已包含在组总量中；未配置费率，费用未知。

十个任务均确认基线复现，十份清单/输入经过运行器校验；十个容器与工作区清理成功，worker stderr 均为空。在线流程和独立计分命令分别为 `python -m evaluation.isolated_agent_ab prepare/run/score --output work/evaluation/rag-ab-context-20261112-45k`，prepare 另传 `--case-ids case-03,case-11,case-12,case-19,case-30 --task-tokens 45000`；`python -m evaluation.agent_ab_analysis --output work/evaluation/rag-ab-context-20261112-45k` 确认十个槽位完整。

结论：纠错重放工具的缺陷已经修正并在线验证，历史案例的动态工具返回已减小；本轮仍未证明 RAG 提高修复成功率。后续若要测收益，应先处理多阶段链路在 120 秒下的耗时问题，再使用独立任务、多次配对及预注册预算评测；不能把本轮开发样例当作正式测试集。
