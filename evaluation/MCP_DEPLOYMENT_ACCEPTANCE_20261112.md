# MCP 与部署可靠性验收记录

- 日期：2026-11-12
- 环境：Windows 本机，项目位于 F 盘；临时服务和测试数据均使用 F 盘路径。
- 性质：本地技术验收，不代表公网生产环境验收。

## MCP 只读服务

- 使用项目 `.mcp.json` 启动 Context7、GitHub 和 Sentry 三个 MCP 服务。
- 初始化按服务独立执行；单服务等待上限为 15 秒，总初始化时限为 60 秒。一个服务连接失败不会阻止其他服务加载。
- 三个服务合计注册 19 个只读工具，完整启动约 35.55 秒，无连接警告。
- 对 Context7 执行文档库解析，对 GitHub 执行公开仓库搜索，对 Sentry 执行组织查询；三项都收到真实服务响应。
- MCP 客户端专项测试：14 项通过，覆盖慢服务和失败服务不阻断后续服务。

本次没有验证任何第三方写操作。已连接配置只开放只读工具，不能据此推断写操作授权、外部副作用核对或第三方回滚有效。

## Docker 执行隔离

真实本机 Docker Engine 29.7.2/Linux 中执行了合成缺陷验收，结果为 `passed`。覆盖修复、复现、pytest、敏感文件遮蔽、只读挂载、网络与能力限制、超时清理、失败回归和结果回传；测试结束后确认容器与工作区清理完成。完整结果见 [docker-acceptance-reliability-cfa56a79af40.json](docker-acceptance-reliability-cfa56a79af40.json)。

模型回复固定、缺陷为合成样例；这证明当前本机容器执行路径在这些场景下工作，不代表公网主机隔离、多租户对抗测试或真实模型修复质量已经通过。

## 本机 API staging

用 F 盘临时 Uvicorn 服务和两个本地测试账号验证：个人记忆按账号隔离，跨账号切换被拒绝。对健康端点发送 100 次请求、并发 16，全部返回 HTTP 200；复测总墙钟时间 4.045 秒，P50 为 33.4 ms，P95 为 42.01 ms。

这只覆盖本机健康端点与账号记忆隔离，不是完整修复链路压测，也没有验证公网反向代理、跨进程部署、真实租户凭证或生产级故障恢复。

## 部署回归

部署专项组合测试为 `115 passed, 1 failed`。唯一失败发生在 20 秒 watchdog 预算场景：整组测试高负载时，测试未能及时到达预期的慢模型调用；单独复测该场景为 `1 passed`。因此单项逻辑复测通过，但整组运行仍有一个未解释的负载敏感失败，不能将组合结果记录为全通过。

另有跨进程熔断半开探针测试：6 个进程竞争时只有 1 个取得探针，其余 5 个被熔断，专项测试通过。

## 未完成的外部验收

- 没有公网 staging 地址，也没有两个线上测试账号，因此公网多租户隔离、真实部署拓扑、反向代理/限流和公网故障恢复尚未验证。
- 当前 MCP 配置为只读，且没有安全可清理的第三方写入测试对象，因此真实 MCP 写操作未验证。
- 本机健康端点的小规模请求结果不能代替全链路压测、容量测试或生产雪崩保护证明。

要完成这些外部验收，需要部署目标服务并准备专用测试租户及可安全删除的测试对象；本地临时 staging 无法替代这些外部条件。
