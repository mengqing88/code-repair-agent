## 逐题说明

### case-181　折扣后满减门槛判定

**缺陷类别**：条件判断引用了变换前的中间量（用折前金额判断满减门槛）。

**问题描述（report）**：促销结算在叠加会员折扣与满减时出现错误：某订单原价 120 元、5 折、满 100 减 15，折后应付 60 元（未达到满减门槛），系统却仍减去了 15 元，实收 45 元。另有多笔原价刚好达门槛、折后远低于门槛的订单被错误减免，甚至被减到 0 元。预期行为：满减条件必须基于折后金额判断，折后未达门槛时不得减免。

**行为契约（contract）**：payable_cents(price_cents, rate_bp, threshold_cents, reduction_cents) -> int，单位分，均为整数。折后金额 discounted = (price_cents * rate_bp + 50) // 100（四舍五入到分，rate_bp 为 0..100 的百分点）。仅当 discounted >= threshold_cents 时才减去 reduction_cents；结果若小于 0 则截断为 0；返回整数分。price_cents < 0、rate_bp 不在 [0,100]、threshold_cents < 0 或 reduction_cents < 0 时抛 ValueError。折后金额与门槛相等视为满足条件；折后金额小于门槛（哪怕只差 1 分）视为不满足。

**相关历史经验**：`experience-181`（相似缺陷机制，不同业务场景 / 函数接口 / 实现）。

### case-182　半开日期区间重叠天数

**缺陷类别**：端点包含性口径错误（半开区间按闭区间计数，系统性 off-by-one 多 1）。

**问题描述（report）**：排期系统统计两段占用日期的重叠天数时结果总是多 1 天：[1,5) 与 [3,8) 应重叠 2 天却返回 3；[1,10) 与 [3,6) 应 3 天却返回 4；仅端点相接的 [1,5) 与 [5,9) 应返回 0 却返回 1。预期：按半开区间 [start, end) 计算，端点相接不算重叠。

**行为契约（contract）**：overlap_days(a_start, a_end, b_start, b_end) -> int，四个参数均为整数天序号。区间语义为半开 [start, end)；重叠天数 = max(0, min(a_end,b_end) - max(a_start,b_start))，返回非负整数。start == end 为空区间，重叠天数恒为 0；两个区间仅端点相接时重叠天数为 0。任一区间 start > end 时抛 ValueError；其它输入均为合法整数，不做额外校验。

**相关历史经验**：`experience-182`（相似缺陷机制，不同业务场景 / 函数接口 / 实现）。

### case-183　嵌套配置递归合并

**缺陷类别**：嵌套结构被整体替换而非递归合并（未指定的默认子键丢失）。

**问题描述（report）**：服务启动时合并默认配置与用户覆盖配置，用户只改了 db.host，结果 db.port、db.pool 等未指定的默认项全部消失，导致连接参数缺失；多层嵌套（svc.auth.ttl）被覆盖时，同级 svc.log 与 svc.auth.algo 也被整体丢弃。用户传入空的嵌套字典 {} 时，原有默认子项同样被清空。预期：嵌套字典按键递归合并，未提及的子键保留默认值。

**行为契约（contract）**：merge_config(defaults: dict, overrides: dict) -> dict，返回新字典且不修改 defaults / overrides。逐键合并：若 overrides 的值与 defaults 中对应值都是 dict，则对该子字典递归合并；否则以 overrides 的值为准。None 是合法的显式覆盖值；新增键直接加入结果；空字典 {} 作为覆盖值时按递归合并语义不改动 defaults 中该键的子键。任一入参不是 dict 时抛 TypeError。返回值只含普通 dict / 标量，不要求深拷贝嵌套中的可变标量。

**相关历史经验**：`experience-183`（相似缺陷机制，不同业务场景 / 函数接口 / 实现）。

### case-184　支付回调的状态守卫与重复入账

**缺陷类别**：状态守卫用「排除单一终态」而非「必须为初始态」，已支付订单被重复推进并重复记账。

**问题描述（report）**：支付回调在订单已 paid 后，用新的 event_id 再次请求仍会成功并再次累加金额，出现一笔订单被扣两次款；连续重试会持续累加。已 paid 的订单再调用 cancel 会被正确拒绝，但随后的新 event_id 付款依旧被接受。预期：除 pending 外的任何状态都不得接受付款回调，重复回调（相同 id 由幂等集合拦截，不同 id 由状态守卫拦截）必须返回 False 且完全不改变状态与累计金额。

**行为契约（contract）**：OrderProcessor() 初始 state='pending'、total_charged=0。apply_payment(event_id, amount_cents) -> bool：按以下顺序判定——(1) event_id 已在已处理集合中则返回 False 且不改变任何状态；(2) amount_cents <= 0 抛 ValueError；(3) 仅当 state == 'pending' 时接受付款：state 置 'paid'、total_charged += amount_cents、记录 event_id、返回 True；其它状态（paid / cancelled）一律返回 False，且不记录 event_id、不改变 state 与 total_charged。cancel() -> bool：仅 pending -> cancelled 返回 True，否则返回 False 且不改变状态。event_id 为任意可哈希值，amount_cents 约定为正整数。

**相关历史经验**：`experience-184`（相似缺陷机制，不同业务场景 / 函数接口 / 实现）。

### case-185　复合缓存键的编码碰撞

**缺陷类别**：多字段复合键用无分隔符拼接，不同组合映射到同一键，导致互相覆盖与误失效。

**问题描述（report）**：指标缓存用 (service, metric) 两段拼成键。上线后发现 ('ab','c') 与 ('a','bc') 会读到同一份数据：后者 put 之后前者 get 到的是后者的值；三段键 ('a','bc','d') 与 ('ab','c','d') 同样冲突。更严重的是对 ('ab','c') 调用 invalidate 会把 ('a','bc') 的条目一起删掉。预期：任意不同的 key_parts 序列必须对应互不干扰的独立缓存条目。

**行为契约（contract）**：MetricsCache 提供 put(key_parts, value) / get(key_parts) / invalidate(key_parts)。key_parts 为非空字符串序列（tuple 或 list），每段只含 [a-z0-9_]，不含 U+001F。value 为任意非 None 的 int；get 命中返回该值，未命中返回 None；put 相同 key_parts 覆盖旧值；invalidate 只删除对应条目，不得影响其它 key_parts。硬性要求：不同的 key_parts 序列必须一一映射到不同缓存条目，绝不碰撞（含 2 段、3 段及更长组合）。

**相关历史经验**：`experience-185`（相似缺陷机制，不同业务场景 / 函数接口 / 实现）。

### case-186　分组求和的累加器重置

**缺陷类别**：累加器在循环体内被重新初始化，同一分组只保留最后一条记录。

**问题描述（report）**：订单日报按类别汇总金额时发现：同一类别出现多笔时，结果只等于最后一笔的金额，前面的记录全部丢失；类别记录不连续（中间穿插其它类别）时同样只保留最后一次出现的值。预期：同一类别无论出现几次、是否连续，都应累加上所有金额。

**行为契约（contract）**：totals_by_category(records) -> dict[str, int]。records 为 (category: str, amount_cents: int) 序列，amount_cents 为非负整数。返回每个 category 的金额总和；同一 category 可多次出现且可不连续；空输入返回 {}；不修改 records；返回值为新字典。

**相关历史经验**：`experience-186`（相似缺陷机制，不同业务场景 / 函数接口 / 实现）。

### case-187　排行榜并列名次

**缺陷类别**：排序键缺少次关键字，同分记录按输入顺序而非约定的名字顺序排列。

**问题描述（report）**：积分榜要求分数相同按用户名升序展示，但当前实现同分时保持了输入顺序：bob 与 alice 同为 10 分却显示 bob 在前；多人同分时顺序完全取决于上游数据顺序。预期：主排序按分数降序，同分按用户名（字典序）升序，结果稳定可复现。

**行为契约（contract）**：rank(players) -> list[tuple[str, int]]。players 为 (name: str, score: int) 序列；返回按 score 降序排列的新列表；score 相同时按 name 的字典序升序排列；不修改 players；空输入返回 []。

**相关历史经验**：`experience-187`（相似缺陷机制，不同业务场景 / 函数接口 / 实现）。

### case-188　未排序输入的按天分组

**缺陷类别**：按连续段分组前未先排序，不连续的同一分组被拆成多段且互相覆盖。

**问题描述（report）**：日志聚合按天统计条数，但上游日志未按天排序。当前实现把同一天出现的多段记录分别计数，后一段的计数会覆盖前一段，导致总数偏小；例如 d1/d2/d1 的顺序下 d1 只统计到 1 条。预期：无论输入顺序如何，同一天的所有记录都应合并统计。

**行为契约（contract）**：count_by_day(entries) -> dict[str, int]。entries 为 (day: str, message: str) 序列，day 为任意字符串且输入**可以无序**。返回每个 day 对应的记录总数；同一 day 出现多次、多次出现之间夹杂其它 day 时都应累加；空输入返回 {}；不修改 entries；返回值为新字典。

**相关历史经验**：`experience-188`（相似缺陷机制，不同业务场景 / 函数接口 / 实现）。

### case-189　无效记录的循环控制流

**缺陷类别**：跳过无效记录时误用 break 提前终止遍历，应为 continue。

**问题描述（report）**：结算脚本汇总有效金额时需要跳过非正数记录，但遇到第一条无效记录就结束了整个遍历，后面的有效金额全部未被计入；无效记录出现在开头时结果直接变成 0。预期：跳过所有 <= 0 的记录，继续处理后续所有正数金额。

**行为契约（contract）**：sum_valid(orders) -> int。orders 为整数列表；遍历**全部**元素，累加所有 amount > 0 的值；amount <= 0 的记录被跳过但不影响后续元素；空输入返回 0；不修改 orders。

**相关历史经验**：`experience-189`（相似缺陷机制，不同业务场景 / 函数接口 / 实现）。

### case-190　库存预警的阈值边界

**缺陷类别**：阈值相等边界使用了严格小于，恰好等于安全库存时未触发补货。

**问题描述（report）**：库存预警规则为「库存低于或等于安全阈值即需补货」，但当前实现在库存恰好等于阈值时不报警，导致临界库存被漏掉；安全阈值为 0 且库存为 0 时同样漏报。预期：stock <= safety_stock 时返回 True。

**行为契约（contract）**：needs_restock(stock, safety_stock) -> bool。stock 与 safety_stock 均为非负整数；当 stock <= safety_stock 时返回 True，否则返回 False；任一参数为负数时抛 ValueError；相等（含双方均为 0）视为需要补货。

**相关历史经验**：`experience-190`（相似缺陷机制，不同业务场景 / 函数接口 / 实现）。

### case-191　可变默认参数导致的跨调用共享

**缺陷类别**：可变对象作为默认参数，未显式传参的多次调用共享同一个列表。

**问题描述（report）**：购物车工具在不传 cart 参数时，本应每次得到一个只含本次商品的新列表，实际上第二次调用会带上第一次的商品，连续调用不断累积；同一个进程里不同业务流的数据互相串在一起。预期：未传 cart 时各次调用互不影响；显式传入列表时仍在该列表上追加并返回同一对象。

**行为契约（contract）**：add_item(item, cart=None) -> list。cart 为 None（未提供）时返回一个只含 item 的新列表，且多次未提供 cart 的调用之间不得共享状态；显式传入 list 时把 item 追加到该列表并返回**同一个列表对象**；item 为任意对象；不修改任何默认值。

**相关历史经验**：`experience-191`（相似缺陷机制，不同业务场景 / 函数接口 / 实现）。

### case-192　浮点金额的精确相等比较

**缺陷类别**：用 == 直接比较浮点金额，未使用容差，浮点误差导致本应相等的金额被判不等。

**问题描述（report）**：对账模块把 0.1+0.2 与 0.3 判为不相等、把 10 个 0.1 的累加和与 1.0 判为不相等，产生了大量误报；相差 1e-12 的两笔金额也被判为不一致。预期：两金额之差的绝对值不超过 1e-9 即视为相等。
