# 评测样例清单（模型：MiniMax-M3.1-Flash）

起始编号 case-151，共 30 个样例。

## case-151 阶梯费率在阈值处未命中对应档位

- **缺陷类别**：阈值边界比较
- **问题描述**：会员消费金额刚好等于某档门槛时，返回了上一档的费率而不是门槛本身那一档，导致临界金额的折扣比预期低一档。
- **行为契约**：tiered_rate(amount, tiers) 返回 amount 对应的费率。tiers 为按门槛升序排列的 (threshold, rate) 列表，rate 为 0~1 的浮点数。规则：若 amount 大于等于某个 threshold，则命中该 threshold 对应的 rate；命中的是满足 amount >= threshold 的最大 threshold 对应的那一档；amount 小于最小 threshold 时返回 0.0。返回值类型为 float。

## case-152 金额四舍五入使用了内置 round 的银行家舍入

- **缺陷类别**：舍入模式
- **问题描述**：结算金额保留两位小数时，明明应该进位的 2.675 被舍成了 2.67，1.005 被舍成 1.00，0.5 取整成了 0，与业务约定的四舍五入（逢五进位）不一致。
- **行为契约**：round_money(amount, places=2) 返回按四舍五入（half-up，逢五进位）保留 places 位小数后的金额，places 为非负整数。实现必须基于十进制语义（Decimal + ROUND_HALF_UP），不能受二进制浮点表示误差影响，也不得使用银行家舍入。返回类型为 float。

## case-153 半开区间重叠判断把相邻区间判为重叠

- **缺陷类别**：区间边界语义
- **问题描述**：排班系统中前一个班次 9:00-12:00 与后一个班次 12:00-15:00 被判定为冲突，导致大量本可衔接的班次无法通过排班校验。
- **行为契约**：ranges_overlap(start, end, other_start, other_end) 判断两个半开区间 [start, end) 与 [other_start, other_end) 是否重叠。重叠当且仅当 start < other_end 且 other_start < end。两个区间首尾相接（end == other_start 或 other_end == start）不算重叠；任一区间为空（start == end）时不算重叠。返回 bool。

## case-154 配置合并只做浅合并，嵌套配置被整体覆盖

- **缺陷类别**：配置合并深度
- **问题描述**：部署配置合并时，只想覆盖 server.timeout，但整个 server 节点被替换掉了，同级未指定的 host、workers 等默认值全部丢失，导致服务启动后用了错误的默认参数。
- **行为契约**：merge_config(defaults, overrides) 返回合并后的新配置字典，且不修改任何入参。规则：若某个 key 在两侧都是 dict，则递归合并（子 key 逐个覆盖）；否则以 overrides 中的值为准；仅在 defaults 中出现的 key 原样保留。仅在 overrides 中出现的 key 原样保留（dict 值也需复制，不与入参共享引用）。

## case-155 配置优先级用真值判断，空串和 0 被当成未设置

- **缺陷类别**：存在性判断
- **问题描述**：运维把某个开关显式配置成空字符串或 0 时，程序没有采用这个配置，而是回退到了默认值，导致关闭开关、禁用功能的操作不生效。
- **行为契约**：resolve_setting(key, overrides, defaults) 返回生效的配置值。规则：只要 overrides 中存在该 key（无论其值是空字符串、0、False 还是 None 之外的其他值），就返回 overrides[key]；仅当 key 不在 overrides 中时返回 defaults.get(key)；两个字典都没有该 key 时返回 None。

## case-156 状态机未校验前置状态，任意状态都能跳转

- **缺陷类别**：状态转换前置校验
- **问题描述**：订单流程中，已取消或已送达的订单居然还能被推进到“已支付”，业务方据此记录了收款流水，造成账目污染。
- **行为契约**：next_state(state, event) 返回执行 event 后的新状态。允许的转移为：NEW→PAID（PAY）、NEW→CANCELLED（CANCEL）、PAID→SHIPPED（SHIP）、SHIPPED→DELIVERED（DELIVER）；DELIVERED 与 CANCELLED 为终态，不允许任何转移。若 state 未知，或在当前状态下不允许该 event，抛出 ValueError，错误信息中包含 state 与 event。

## case-157 退款按比例分摊时逐项四舍五入，总额与退款额对不上

- **缺陷类别**：金额分摊与舍入
- **问题描述**：一笔 100 元退款按三笔订单平均分摊后，各笔退款额相加为 99 元而不是 100 元；对账时系统判定金额不平，剩余 1 分无处可去。
- **行为契约**：allocate_refund(total, weights) 将 total 按 weights 比例分摊，返回一个整数列表（单位：分）。规则：weights 为空时返回空列表；weights 之和必须大于 0（否则抛出 ValueError）；返回值长度等于 len(weights)；各元素非负；返回值之和必须严格等于 total；分摊采用最大余数法：先按比例向下取整，再把剩余的分按小数部分从大到小依次补给各元素，小数部分相同时按 weights 的原始下标从小到大补给。total 为非负整数（分）。

## case-158 账单分期按月份数平均分摊，忽略了各月实际天数

- **缺陷类别**：日期驱动的金额分摊
- **问题描述**：账单分期在包含 2 月（28 天）的月份里，每期金额与合同约定的按实际天数分摊结果不一致，冬季账单比夏季账单每期少扣了钱。
- **行为契约**：split_bill(total_cents, days_of_months) 将总额按各月天数比例分摊，返回整数列表（单位：分）。规则：days_of_months 必须是非空列表且每项为正整数（否则抛出 ValueError）；返回长度等于 len(days_of_months)；使用最大余数法分摊（先向下取整，剩余分按小数部分从大到小补，余数相同时按下标从小到大补）；各元素之和严格等于 total_cents；total_cents 为非负整数。

## case-159 多来源配置合并时 None 值被当作有效取值

- **缺陷类别**：配置优先级
- **问题描述**：在配置中心把数据库连接串留空（未配置）时，合并结果里出现了一个 None 值，反而把低优先级的兜底配置挡掉了，连接串变成 None。
- **行为契约**：merge_sources(sources) 按列表顺序合并多个配置来源，返回新的扁平字典，且不修改入参。规则：靠前的来源优先级更高；同一 key 出现在多个来源时，取优先级最高的来源（列表中下标最小者）的值；某个来源的值为 None 视为“该来源未提供该 key”，应跳过并让后续来源生效；所有来源都不提供该 key 时该 key 不出现在结果中。

## case-160 幂等存储重复写入时覆盖了首次响应

- **缺陷类别**：幂等与重复请求
- **问题描述**：同一个请求因网关重试被处理了两次，第二次写入的响应覆盖了第一次已经返回给客户端的响应，客户端拿到的是与首次不一致的结果。
- **行为契约**：IdempotencyStore 维护 request_id -> response 的幂等映射。check_and_get(request_id)：若该 request_id 已被 remember 过，返回已存的响应对象（与写入时同一对象，恒等相等）；否则把 request_id 标记为已见并返回 None。remember(request_id, response)：写入 request_id 对应的响应；若该 request_id 已有响应，必须保留首次写入的响应而不得覆盖。规则：request_id 为空字符串或 None 时抛出 ValueError；不同 request_id 相互独立；只保留最近 capacity 条记录，超出后淘汰最早写入的一条。

## case-161 CSV 记录解析手工切分，破坏带引号的字段

- **缺陷类别**：数据解析
- **问题描述**：导出对账单时，商品名称里带逗号的记录（如 "T恤, 短袖"）解析后只剩前半段，后续库存统计全部偏低。
- **行为契约**：parse_records(text) 解析 CSV 文本，返回字典列表。规则：必须用标准库 csv 模块整体解析，支持带引号字段、字段内逗号与转义双引号；第一行是表头，键名即表头字段名；忽略完全空白的行；某条记录列数少于表头时，缺失的列不出现在该记录字典中；列数多于表头时，多余的值放入键 "_extra" 的列表中；text 为空或仅空白时返回空列表。

## case-162 分组取最新记录时取成了组内最早的一条

- **缺陷类别**：分组与排序
- **问题描述**：按用户取最新一条订单时取到了该用户最早的那条订单，报表展示的是历史订单而不是最新订单。
- **行为契约**：latest_by(rows, key) 按 key 分组并返回每组最新的一条记录，rows 为 dict 列表，每条含 "key" 与 "ts"（整数时间戳）。规则：组内最新定义为 ts 最大的那条；ts 相同时取在原列表中靠后出现的那条；返回列表按 key 升序排列；rows 为空时返回空列表；不修改入参。

## case-163 月末日期计算固定返回 30 日

- **缺陷类别**：月末与闰年计算
- **问题描述**：账期生成时，二月的截止日期被算成 30 日（2 月只有 28 天的年份也算 30 日），三月的截止日期也少了 1 天，导致每月账单周期比实际多一天或少一天。
- **行为契约**：month_end(year, month) 返回该年该月的最后一天，返回类型为 int。规则：month 必须是 1~12 的整数，否则抛出 ValueError；31 天的月份返回 31；30 天的月份返回 30；2 月在闰年返回 29、平年返回 28；闰年判定遵循公历规则（能被 4 整除且不能被 100 整除，或能被 400 整除）。

## case-164 闰年判定只按能否被 4 整除，世纪年被误判

- **缺陷类别**：闰年判定
- **问题描述**：1900 年被当成闰年，2 月被多算了一天，日历类功能的年份偏移逐日累积错误。
- **行为契约**：is_leap_year(year) 返回 bool。规则：遵循公历闰年规则——能被 400 整除的年份是闰年；能被 4 整除但不能被 100 整除的年份是闰年；其余不是闰年。year 为负数时按绝对值判定。

## case-165 多关键字排序只用了第一个关键字

- **缺陷类别**：多关键字排序
- **问题描述**：工单列表按优先级排序后，同优先级的工单之间顺序错乱，期望按创建时间从早到晚排列，实际是输入顺序。
- **行为契约**：sort_orders(orders) 返回按 (priority 降序, created_at 升序) 排序后的新列表，不修改入参。orders 为 dict 列表，每条含 "priority"（整数，越大越优先）与 "created_at"（整数时间戳）。规则：priority 大的排在前面；priority 相同时 created_at 小的排在前面；两个关键字都相同时保持原有相对顺序（稳定排序）。

## case-166 缓存键直接拼接参数，产生了键冲突

- **缺陷类别**：缓存键冲突
- **问题描述**：缓存里偶尔取到别的请求的数据：租户 A 的用户 "ab" 与租户 B 的用户 "bc" 被拼成了同一个缓存键，互相覆盖。
- **行为契约**：cache_key(*parts) 返回缓存键字符串。规则：由所有 part 依次拼接而成，拼接时必须保证不同的 part 序列不会产生相同的键——即结果可逆；part 内的分隔符与转义符必须被转义；parts 为空时返回空字符串；所有 part 必须是字符串或整数（其他类型抛出 TypeError）。

## case-167 缓存淘汰策略错误地淘汰了最久未使用的条目

- **缺陷类别**：缓存淘汰策略
- **问题描述**：缓存容量满后，被淘汰的不是最久没访问的条目，而是刚被访问过的那个，导致热点数据反复被重建。
- **行为契约**：LruCache 实现最近最少使用淘汰。接口：put(key, value) 写入；get(key) 读取，命中时把该条目标记为最近使用，未命中返回 None；超过 capacity 时淘汰最久未使用的条目。规则：capacity 必须为正整数（否则抛出 ValueError）；get 命中会更新使用顺序；淘汰发生在 put 之后，容量不超过 capacity；key 必须是字符串。

## case-168 状态匹配用了前缀比较，相似状态被混淆

- **缺陷类别**：状态匹配
- **问题描述**：流转规则里 PENDING 和 PENDING_REVIEW 被当成同一个状态，导致待审核的工单无法走到审核通过分支。
- **行为契约**：can_transition(current, target) 返回 bool，判断 current 状态能否直接流转到 target 状态。规则：状态名必须完全相等才算同一状态，不允许前缀或子串匹配；current 与 target 都是字符串；流转白名单为 {PENDING: {PENDING_REVIEW, CANCELLED}, PENDING_REVIEW: {APPROVED, REJECTED}, APPROVED: {CLOSED}, CLOSED: set()}；只有白名单允许的组合返回 True；未知状态一律返回 False。

## case-169 区间求和时右端点被重复计入

- **缺陷类别**：日期区间边界
- **问题描述**：统计某个闭区间的订单金额时，区间右端点那天的订单被算了两遍，月度汇总比实际多出一笔。
- **行为契约**：sum_in_range(rows, start, end) 统计 rows 中满足 start <= "day" <= end 的记录金额之和，返回 int。rows 为 dict 列表，每条含 "day"（形如 "2024-03-05" 的字符串）与 "amount"（整数分）。规则：区间两端都包含（闭区间）；只统计 day 落在区间内的记录；start > end 时返回 0；不修改入参。

## case-170 限制器令牌桶补充令牌时按整秒计算，短窗口内限流不准

- **缺陷类别**：限流与令牌补充
- **问题描述**：限流器在 1 秒窗口内本应放行 2 个请求，实际只放行了 1 个，短时突发流量被误杀。
- **行为契约**：TokenBucket 令牌桶。构造参数 rate（每秒补充的令牌数，必须为正数）与 capacity（桶容量，必须为正整数）。acquire(tokens=1) 尝试取令牌：成功返回 True；桶内令牌不足时返回 False，不做等待。规则：初始桶内令牌数为 capacity；每经过 elapsed 秒补充 elapsed * rate 个令牌，上限为 capacity；令牌数为浮点数，允许小数累积；tokens 必须为正整数，否则抛出 ValueError。

## case-171 折扣叠加时忽略了互斥规则，两种折扣同时生效

- **缺陷类别**：折扣规则互斥
- **问题描述**：一张同时满足会员折扣和满减券的订单，两个折扣都被应用了，订单金额低于成本，客服收到大量投诉。
- **行为契约**：apply_discounts(amount, member_rate, coupon) 计算最终应付金额，返回 int（单位：分）。规则：amount 必须为非负整数，member_rate 为 0~100 的整数（会员折扣百分比），coupon 为整数减免金额（分，可为 0）。若 coupon > 0 且 member_rate > 0，则二者互斥：只应用 member_rate 对应的折扣，coupon 被忽略；否则只应用非零的那一个；两个都为 0 时返回 amount；最终金额不得小于 0。

## case-172 分组统计时把累计值写到了共享的临时变量上

- **缺陷类别**：分组聚合
- **问题描述**：按门店分组统计销售额时，某个门店的金额只在连续出现的那些行里被累加，门店数据一旦被其他门店行打断，该门店的总计就被覆盖成了最后一次的金额，逐店报表完全错误。
- **行为契约**：totals_by_group(rows, key) 按 key 分组求和，返回 dict。rows 为 dict 列表，每条含 key 指定的分组字段与 "amount"（整数分）。规则：结果字典的键为分组值，值为该组所有记录的 amount 之和（int），无论该组的记录在入参中是否连续出现；结果中不出现入参里没有的分组；不修改入参；rows 为空时返回空字典。

## case-173 数值文本解析时把无效行静默跳过，坏数据被吞掉

- **缺陷类别**：数据解析与错误处理
- **问题描述**：导入的订单金额文本里混进了非法行（单位后缀、货币符号），这些行被悄悄丢弃，导致导入条数比源文件少，但没有任何报错提示。
- **行为契约**：parse_amounts(text) 把多行文本解析成整数金额列表，返回 list[int]。规则：文本按行拆分（换行符 \n 或 \r\n）；忽略完全空白的行；每行去掉首尾空白后必须是由十进制数字组成的非负整数（允许前导零），否则必须抛出 ValueError，且错误消息中包含该行的原始内容；结果按行顺序返回；text 为空字符串时返回空列表。

## case-174 金额比较用字符串相等判断，数值相同但写法不同的金额被漏掉

- **缺陷类别**：金额比较与类型归一
- **问题描述**：对账脚本比对金额时，字符串 "100" 和整数 100 被认为不相等，产生了大量假差异告警。
- **行为契约**：amounts_equal(left, right) 判断两个金额是否相等，返回 bool。规则：金额可以是 int、float 或它们的字符串形式；比较前把字符串形式解析为数值（数值字符串前后允许有空白；无法解析的字符串视为不相等而不是抛异常）；数值相等即视为金额相等（包括 100 与 100.0、"100" 与 100）；无法解析的一侧与可解析的一侧比较返回 False。

## case-175 排序时把浮点分数当整数比较，比较方向反了

- **缺陷类别**：数值排序与比较方向
- **问题描述**：排行榜里评分 9.6 的用户排在了评分 8.2 的用户后面，排名与评分完全相反。
- **行为契约**：rank_users(users) 返回按 score 降序排序后的新列表，不修改入参。users 为 dict 列表，每条含 "name"（字符串）与 "score"（数值，可为整数或浮点）。规则：score 大的排在前面；score 相同时保持原有相对顺序（稳定排序）；不修改入参；空列表返回空列表。

## case-176 百分比折扣按单价计算而不是按订单总额计算

- **缺陷类别**：折扣计算基数
- **问题描述**：多件商品的订单，整单 8 折没有按总额算，而是每件商品各自打了 8 折再相加，凑单优惠反而多收了钱。
- **行为契约**：order_total(unit_cents, quantity, discount_percent) 返回订单应付金额（int，单位分）。规则：先计算小计 = unit_cents * quantity；再按小计计算折扣 = 小计 * discount_percent // 100（整除，向下取整）；最终金额 = 小计 - 折扣；quantity 必须为正整数，否则抛出 ValueError；discount_percent 必须在 0~100 之间，否则抛出 ValueError；unit_cents 必须为非负整数。

## case-177 状态流转白名单查反了方向，合法流转被判为非法

- **缺陷类别**：状态机与白名单方向
- **问题描述**：工单状态流转全部被拒绝，明明允许从"处理中"转到"已完成"的工单也提交不了，业务被卡住。
- **行为契约**：can_advance(state, target) 返回 bool。规则：state 与 target 均为字符串；允许的流转白名单为 {"0": {"1"}, "1": {"2", "9"}, "2": set(), "9": set()}，即 ALLOWED[当前状态] 给出允许到达的目标状态集合；只有白名单中明确列出的组合返回 True，其余一律返回 False；state 为空字符串或 None 时返回 False。

## case-178 去重时用了集合再排序，顺序被改成了字典序

- **缺陷类别**：去重与顺序保持
- **问题描述**：商品列表去重后顺序完全变了，运营按顺序投放的橱窗位被打乱。
- **行为契约**：dedupe_keep_order(items) 返回去重后的新列表，保持首次出现的相对顺序。规则：按元素相等性去重（不可变元素）；不修改入参；空列表返回空列表；结果不要求有序，但必须保持首次出现的顺序。

## case-179 嵌套配置合并时把列表当成标量覆盖，列表元素丢失

- **缺陷类别**：嵌套列表合并
- **问题描述**：覆盖配置里给某个服务加了一条路由列表，结果整个列表被替换成了只有一个元素的列表，原有的其他路由全部消失。
- **行为契约**：merge_config(base, override) 返回合并后的新字典，不修改入参。规则：两个来源中同 key 的值都是 dict 时递归合并；都是 list 时按元素逐个合并——override 的列表中每个元素按其索引与 base 对应元素合并，索引超出 base 长度的部分直接取 override 的元素；base 有而 override 没有的元素保留；值类型不同（dict vs 非 dict、list vs 非 list）时以 override 为准；override 中值为 None 表示该 key 未提供，保留 base 的值。

## case-180 追加写入时用了浅拷贝追加，多个记录共享同一个字典

- **缺陷类别**：浅拷贝与共享引用
- **问题描述**：日志记录追加到列表后，修改其中一条记录影响了所有记录，所有日志内容都变成了最后一条。
- **行为契约**：append_records(records, new_record) 把 new_record 追加到 records 并返回新列表。规则：必须深拷贝 new_record 与其内部的嵌套 dict/list，追加后的记录与传入的 new_record 之间不得共享可变对象；不修改传入的 new_record；records 本身不修改（返回新列表）；new_record 必须是非空 dict，否则抛出 ValueError。
