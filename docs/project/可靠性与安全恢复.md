# 可靠性控制与安全恢复

以下是当前可配置、可验证的执行规则。配置模板没有真实凭据，修改模板不会自动修改本机 `.env` 或 MCP 授权。

## 重复动作与状态迁移

- ReAct 对工具名、规范化参数和返回内容取摘要；错误对象排除每次不同的诊断编号、请求编号和记录时间，成功返回中的真实版本与时间不丢弃。同一动作和结果第 2 次出现时提示换方法，第 3 次暂停为 `agent_no_progress`；变化的返回内容不算同一结果。一次补丁生成仍受 60 次工具调用和原有时间、Token、费用上限约束。
- 暂停任务可经原有澄清接口补充线索后继续。重复检测是有限启发式，不能判断所有语义上的无进展。
- `TaskStore._write` 是状态迁移的统一校验点；节点启动位置和提交后的路由也必须与持久进度一致。进入人工审核要求同一补丁哈希的验证、独立审查通过；进入成功还要求人工接受及经验保存完成。
- 恢复、预算追加、失败任务重投有各自的服务端内部迁移权限；HTTP 输入和模型不能自行指定这些权限。终态结果不能被普通写入覆盖。

## 外部写入 Outbox

1. 用户批准准确的目标和参数时，授权和 Outbox 记录在一个 SQLite 事务内保存。
2. 消费批准时，授权状态、`prepared`（已准备、确认未发送）操作意图和 `ready` 投递状态再次原子提交。
3. 投递前重新核对用户、角色、白名单、Schema、冻结配置、剩余预算和 worker 写入资格，再通过事务把记录改为 `delivering/started`。关键 Trace 必须落盘，才调用外部工具。
4. 正常回执与 `completed` 状态一起保存。相同批准的再次调用读取回执；`delivering/unknown` 不自动重发，先走状态查询或人工核对。
5. `pending/ready` 可以在安全恢复后的补丁节点继续投递；批准已过期则拒绝。Outbox 在现有任务工作流内派发，没有独立的无限后台发送器。

授权记录 ID 同时是稳定的下游幂等键，随 MCP `_meta.code_repair.idempotency_key` 发送。若服务需要显式参数，配置写工具的 `idempotency_argument`；服务 Schema 必须把它定义为字符串。该字段对模型隐藏并禁止模型提供，真正发送时由服务端填入。`status_query.argument_map` 可将查询参数映射到该字段，按同一个键核对结果。

这不能单方面保证第三方 exactly-once：下游必须实际保存并检查幂等键，才能可靠去重。下游不支持时仍采用“结果不明就停、保留锁、不得盲重试”的策略。旧版“授权已消费但没有操作意图”的记录仍判结果未知，不能假定尚未发送。多个未知操作必须全部处理；只处理一个不会恢复整个任务。

## 失败隔离与受控重投

- 任务空闲后，失败、明确超时、重复动作暂停和未知结果暂停会与任务状态同事务写入死信表；每个任务至多一条未处理记录。
- `GET /api/dead-letters?limit=100` 仅返回登录用户自己的记录。
- `POST /api/dead-letters/{id}/decision` 使用原有登录、归属和 CSRF 校验，请求例如：

```json
{"decision":"requeue","request_id":"retry-20261117-01","reason":"已修复服务配置，申请继续排查"}
```

`decision` 可为 `requeue` 或 `dismiss`。同 `request_id` 同参数不会重复消费额度，更换参数冲突。每任务最多 3 次成功重投；每次消耗原有一次修复额度，时间、Token、费用均不补充。预算不足需先走预算追加接口；不能靠重投绕开限制。

有在途节点、未结请求、未知写结果、未停止 worker 或人工审核决定的任务禁止重投。重投前验证执行清单，再恢复任务基线；恢复耗时计入任务时间。改文件前先持久化恢复意图，恢复中途再次崩溃时保留意图、扣除已耗预算并暂停人工核对。它不会以清空错误来跳过恢复，也不会撤销第三方数据变更。当前提供 API，未新增死信专用前端面板。

## 用户级 MCP 身份和受控降级

模板见 [`deploy/mcp.identity.example.json`](../../deploy/mcp.identity.example.json)。

- `service_account` 保留兼容的服务账号行为；`per_user` 必须按服务端账号 ID 配置 `principal_bindings`，每个用户配置独立上游凭据、`subject` 和允许的工具子集。
- HTTP 使用绑定内的 `headers`，stdio 使用绑定内的 `env`；它们完整替换服务共享凭据。缺用户绑定或对应凭据就拒绝，不能回落到共享账号。`subject` 和 `_meta` 是审计信息，不能代替上游认证；上游权限仍必须按最小权限配置。
- 只读工具可配置同服务 `fallback_tool`，熔断按端点和工具分别计数，避免主工具的熔断同时阻断备用。仅瞬时错误在原有有界重试后允许降级，备用工具也要通过白名单、角色权限和 Schema，并共享原任务剩余预算；禁止写操作降级、级联备用和循环。备用工具需由管理员确认语义适用，程序不能自动证明两工具等价。
- 该功能不自动签发 OAuth Token、不替用户创建第三方账号，也不更换冻结的模型供应商。已有服务不会因增加模板自动切换身份。

## PostgreSQL 跨实例资源锁

通过 `REPAIR_COORDINATION_DB_URL` 指向各实例共同的 PostgreSQL 协调库；不输出或提交真实 DSN。连接用户需要创建协调表/序列的权限，网络和数据库权限须独立管理。

- 多个独立数据目录的实例以“服务端点＋资源标识”为同一锁键，争抢持久资源声明；全局递增令牌随 MCP 元数据发送。
- 声明不会因 TTL 到期或持有者进程退出自动消失。结果未知时保留锁，确认操作结果后才能释放；否则旧请求仍可能晚到并与新请求冲突。
- 释放必须匹配安装身份、操作 ID 和令牌；旧令牌不能释放新锁。释放失败保存 `release_pending`，之后补做；数据库不可用就阻止写入，绝不静默回退为本机锁。
- 首次使用时绑定协调库的持久身份；后续缺配置或改到另一个数据库均拒绝。已有本机未结锁时禁止直接启用共享模式；部署切换前必须处理旧在途任务。凭据轮换可以指向同一数据库，删除并重建协调库则需要单独迁移。
- 默认未配置时仍使用单机 SQLite 资源锁。一个数据目录依然只运行一个 API/CLI worker 服务；这次没有把任务队列改成多机共享调度。下游不检查令牌时，不能宣称具备端到端写入栅栏。

## CLI 持久化和恢复

普通 CLI 新任务把业务进度、原生图检查点、执行身份和副作用回执保存在项目 `work/`。恢复命令如下：

```powershell
.venv\Scripts\python.exe -m code_repair.agent_cli resume --data-root .\work
.venv\Scripts\python.exe -m code_repair.agent_cli resume --data-root .\work --task-id <32位任务ID>
.venv\Scripts\python.exe -m code_repair.agent_cli worker --data-root .\work
```

`resume` 做一次安全恢复并执行可运行任务；`worker` 启动时恢复，再持续处理持久队列。CLI 默认数据目录为 `work/`，Web 默认是 `work/web/`，必须传入任务实际所在目录；同目录不能同时运行两种服务。

安全恢复共用 Web 的旧 worker 停止、执行纪元、预算记账、清单核对和未知副作用规则。只读/已记账的模型节点在没有未结请求及未知写结果时可继续；用户代码已经开始但结果不明则暂停，不盲重跑。旧 CLI 只有图数据库、没有业务执行记录的任务不能伪造迁移。CLI PostgreSQL 写入不能用本地 SQLite 缺记录证明未执行，缺少可信上游回执时暂停核对；目标库身份也受绑定检查。

## 验证入口

```powershell
.venv\Scripts\python.exe -m pytest tests/test_reliability_controls.py tests/test_dead_letters.py -q
.venv\Scripts\python.exe -m evaluation.coordination_acceptance --output evaluation/coordination-acceptance-local.json
```

第二条创建唯一名称、随机密码、仅回环端口、带归属标记的一次性 PostgreSQL 容器，运行跨进程锁、旧令牌、重启后待释放记录和故障关闭测试后清理容器及匿名卷。不会读取业务数据库 DSN，也不会停止其他容器。实际结果以报告和根目录项目记录为准；模拟 MCP 测试不等于真实第三方幂等或公网生产验收。
