# 最终补丁生成评测集要求

本文规定如何构建和使用专门衡量 Agent **最终补丁是否有效**的评测集。重点是候选补丁能否修复原缺陷、保持既有行为并遵守修改范围；模型文字解释、补丁与参考答案的相似度、检索命中率都不能代替独立执行结果。

本文是数据和计分规范，不代表已有数据已满足准入要求，也不表示现有计分器已经实现全部检查。完整工作流、RAG、工具、安全及成本评测另见[通用评测要求](评测要求.md)。

## 一、评测范围

每个任务提供固定基线源码、缺陷报告、明确的预期行为、运行环境和 Agent 可见上下文。Agent 输出最终 unified diff；独立评测器将补丁应用到干净基线，在隔离副本运行冻结测试，再检查补丁范围和结果。

将两种实验分开报告：

| 轨道 | 固定条件 | 能回答的问题 |
| --- | --- | --- |
| 补丁生成单项 | 给定相同的已确认缺陷、源码证据和允许的历史经验；不让被比较组件自行复现、检索或调用不同工具 | 补丁生成阶段拿到相同有效信息时，能否产出正确补丁 |
| Agent 端到端 | 从原始任务入口运行真实完整工作流，保留复现、RAG、工具、预算和验证阶段 | 整个 Agent 产品能否完成任务；失败会包含上游和下游原因 |

端到端成绩不能单独归因于补丁生成。若要定位补丁 Agent 本身，应提供已独立验证的相同上下文；这类诊断分数与端到端成绩分栏，不混算。

## 二、样例准入

### 可修复任务

进入主要修复率分母的任务必须满足以下条件：

1. 基线版本、依赖和执行命令可复现，且缺陷验收测试在基线上因目标行为失败。
2. 基线既有测试可执行；已有失败逐项登记，并在运行前定义判定方式。
3. 预期行为有 Issue、契约、版本变更或可信人工说明等依据。仅有作者猜测的不作为正式答案。
4. 参考修复能在基线中应用；相同的既有测试、独立验收测试和原复现检查在参考修复后达到预先规定的结果。
5. 任务允许修改的文件、固定测试范围、语言/运行时和依赖可确定。

收集错误、运行时缺失、下载失败、环境故障、测试自身异常、题目描述冲突和基线不能复现，都不能当作 Agent 修复失败后继续留在“有效修复题”中。它们应修题后再准入，或移到单独的基础设施／澄清／安全行为集合，按其目标评分。

参考补丁用于证明样例有效，不要求模型生成相同文本、文件顺序或算法写法。只要行为、接口和修改范围满足独立答案，多个合理实现均可通过。

### 覆盖面

先按真实项目的缺陷分布制定覆盖矩阵，再招募任务。至少记录并覆盖适用的：

| 维度 | 示例 |
| --- | --- |
| 缺陷行为 | 边界条件、状态更新、异常处理、排序/去重、资源释放、并发、权限、序列化 |
| 规模与结构 | 单文件、多文件、跨模块调用、公开 API、内部实现 |
| 输入边界 | 空值、零、最大/最小值、Unicode、重复输入、异常类型、顺序变化 |
| 任务条件 | 信息完整、需要多个文件证据、依赖/版本约束、合理行为有多种可能 |
| 修改风险 | 公共接口兼容、数据迁移、文件系统、并发状态、安全敏感路径 |
| 语言与环境 | 项目实际支持的语言、运行时版本、依赖管理与测试框架 |

任务分组应反映来源和难度，不能只选容易、单文件、纯函数题。每类报告数量和通过率；整体平均不能掩盖关键类别失败。某维度没有足够样本时标记“样本不足”，不外推结论。

### 数据来源与授权

优先采用可追溯的真实 Issue/修复提交、经授权的历史任务或清楚标注的合成题。每题记录许可证或使用授权、来源链接/标识、采集时间、仓库和基线提交。禁止把私有源码、个人数据、凭据、未授权工单或供应商保密输出放进公开数据集。

真实、合成、公开缺陷和模型生成样例分别标注并分别报告。模型生成的报告、补丁或测试不能被称为人工标注真值；如果模型参与造题或写预期答案，必须披露，并由未参与生成的人复核。

## 三、样例记录和文件隔离

每个案例至少应有以下可审计字段：

| 字段 | 要求 |
| --- | --- |
| `case_id`、`dataset_version`、`split` | 稳定唯一 ID、不可变数据集版本、dev/validation/test 划分 |
| `provenance` | 来源类别、仓库/Issue/提交标识、许可证或授权、采集日期、合成方法（如适用） |
| `group_id` | 仓库、缺陷家族和近重复任务组成的泄漏组 |
| `language`、`runtime`、`dependencies` | 明确的语言版本、运行时、锁文件和必要系统前提 |
| `base_revision`、`source_sha256` | 基线完整 commit 或源码快照哈希；不能只记可变分支名 |
| `report`、`expected_behavior` | Agent 可见的原始描述及经过复核的预期行为/契约 |
| `reproduce_command` | 固定复现入口、所需环境变量名称（不含秘密）和超时 |
| `allowed_paths`、`protected_paths` | 允许修改和必须只读的文件/目录 |
| `existing_test_manifest` | 既有测试命令、预期收集数量、基线结果和哈希 |
| `oracle_manifest` | 隐藏验收测试、原复现后验、测试期望结果及其哈希；仅评测器持有 |
| `reference_patch_hash` | 审核过的参考修复哈希；补丁正文仅在评测器答案侧 |
| `review` | 标注人、独立复核人、分歧及裁决依据、完成日期 |

将 Agent 输入和评测答案物理分开，例如：

```text
dataset-v1/
  manifest.json                 # 版本、哈希、划分、运行约定
  agent-input/<case_id>/        # 基线源码、报告、可见契约和必要上下文
  grader-only/<case_id>/        # 隐藏验收、参考补丁、标签与判分规则
  results/<run_id>/             # 原始补丁、验证结果、trace、诊断和汇总
```

运行环境只挂载当前案例的 `agent-input`，隐藏测试、参考补丁、其他案例答案、标签、生成脚本和计分逻辑不得处于 Agent 可读路径、RAG 语料、MCP 可读资源或同一可枚举容器挂载中。评分前校验所有输入/答案哈希；数据修改必须生成新版本，不覆盖已发布版本。

## 四、隐藏测试和题目有效性

每个可修复案例都应包含：

- **原复现检查**：确认原报告描述的问题在基线出现，参考补丁后消失。
- **缺陷验收测试**：验证报告中的预期行为，并尽量覆盖边界与副作用；基线按约定失败，参考补丁通过。
- **既有回归测试**：检查不相关的原行为没有退化；通过数量、跳过和已有失败均冻结。
- **修改范围检查**：拒绝对隐藏测试、评测器、依赖锁、受保护文件及未授权目录的改动。

所有测试在补丁前后使用相同的固定副本和命令；需清理状态的测试在干净副本中执行。收集失败、无测试、空测试、全部跳过、`xfail` 伪装、语法/依赖错误和基础设施超时都不能算缺陷验收失败或修复通过。

用变异检查验证隐藏测试确实能区分正确和常见错误实现：至少对正确实现与若干典型错误实现执行；若错误实现通过，补测试或把盲点写入已知限制。测试必须断言实际输出/状态，不可只断言代码运行不报错。题目自检通过、参考补丁通过，不等于 Agent 已通过；两类成绩分开存储。

Agent 生成的回归测试可作为额外证据，但不能替代隐藏验收：测试可能迎合候选补丁、遗漏行为或无实际断言。它生成或修改的测试不得进入最终分母作为唯一通过依据。

## 五、划分、防泄漏和冻结

按 `group_id` 分组后再划分 dev、validation、test；同一缺陷的改写、相邻提交、同一修复系列、相同错误函数或可互相推导的题目不能跨组。划分前计算源码/报告规范化哈希，并用文本、AST、补丁和仓库历史排查近重复。所有去重规则、人工判断与排除理由保留记录。

真实缺陷使用按时间切分作为优先方案：评测时的可见源码和经验库不能包含该任务之后才出现的修复、Issue 评论或答案。跨语言、跨版本或跨仓库的题目只有在确认不暴露同一解法时才可分到不同集合。

冻结前生成不可变 manifest，绑定每题输入、测试、答案、来源清单、运行环境、评分规则和划分文件的 SHA-256。冻结测试集不能用于调提示词、选择模型、调 RAG 权重或反复挑补丁；发生改动应发布新版本，并记录旧版本是否仍可比较。

已有 `evaluation/incoming/` 的候选题完成过结构与执行自检，但目前文档标记 `formal_eligible=false`，仍需独立复核、许可/来源复查及冻结准入。不能把 162 个参考补丁通过数称作 Agent 最终补丁生成成绩；接入正式集前必须按本文件重新审查和绑定隐藏验收。

## 六、运行协议

正式运行前预注册：评测目标、主指标、任务集合和划分、重复次数、模型/版本、提示词、工具与权限、RAG 和知识快照、温度/采样参数、每题预算、超时、执行镜像、测试命令及判定规则。无法冻结的外部版本或动态服务要记录未知项，不能声称可完全复现。

每次运行：

1. 从同一冻结基线创建全新只读/可写范围受限的任务副本；清除上次生成文件、个人记忆、缓存和临时数据库。
2. Agent 只读取题目允许的上下文；评分器在隔离面运行隐藏测试和答案检查。
3. 保存原始模型最终补丁、解析结果、实际改动文件、应用结果、源码哈希、测试收集/执行结果、trace、token/费用/耗时与退出原因。
4. 每次重复运行单独存放，不得人工从多个答案挑最好的一份替代主结果。
5. 对照组使用同一案例和相同环境/权限/预算；只允许预注册的因素不同。报告逐题配对差异。

若重复采样，至少报告每题首次独立生成结果和所有预注册运行；`pass@k` 单独标注 k。对每题挑最好补丁只能叫 best-of-k 诊断，不能替代 pass@1 或日常单次运行成绩。不同运行使用隔离副本，禁止前一轮补丁/经验泄漏到后一轮。

## 七、主指标与硬性通过

**单次最终补丁通过率（pass@1）**为主要指标：全部预注册可修复案例的首次独立运行中，通过下列所有硬条件的任务数，除以全部可修复案例数。没有输出、非法 diff、测试超时、基础设施故障及未完成任务仍留在总数中，按预先规定单列失败原因；不能事后移出分母。对确认由评测器/环境自身导致的无效运行，应由独立复核人员按冻结规则判 invalid，并公开数量、原因和重跑记录。

一个最终补丁只有同时满足以下条件才计为通过：

1. 是完整、可解析并能应用到指定基线的补丁；没有人工挑选或修补模型输出。
2. 只修改允许的产品源码和预先许可文件；不修改/删除/跳过测试、评测器、工作流门禁或保护配置来造成功能通过。
3. 隐藏缺陷验收和补丁后的原复现全部达到冻结预期。
4. 固定既有回归测试满足冻结判定，无新增非预期失败、跳过或收集错误。
5. 修改路径、补丁范围和源码证据与最终评分的补丁哈希一致；评分后源码变动必须重跑。

不要求与参考 patch 文本相同，也不允许按 diff 行数、函数名或模型自评直接判正确。对等价但未被自动测试覆盖的实现，先记为“人工复核”，完成盲审后才能按预注册规则确认；盲审失败或未完成时不计自动通过。

同时公布以下指标及明确分母：

| 指标 | 口径 |
| --- | --- |
| 最终补丁 pass@1 | 满足全部硬条件的案例数 / 全部预注册可修复案例 |
| 补丁输出率 | 返回非空候选的运行数 / 全部运行；不代表正确率 |
| 补丁解析/应用率 | 可解析且应用到基线的运行数 / 全部运行 |
| 缺陷修复率 | 隐藏验收与原复现通过的运行数 / 全部可修复案例 |
| 回归通过率 | 满足既有测试冻结规则的运行数 / 全部可修复案例；同时给测试执行覆盖率 |
| 范围合规率 | 未修改受保护/未授权路径的运行数 / 全部运行 |
| 澄清/拒绝精确率与召回率 | 仅在单独的非修复目标集合中按 `clarify`/`reject`/`pause` 标注计算 |
| P50/P95 延迟与 Token/费用 | 包含失败、重试和超时；未知用量单列，不填 0 |

每个指标报告总数、分子、分母、数据来源、运行覆盖率和 95% 置信区间。分母为 0 或数据不可观测时写 `N/A`。修复成功率不能与“补丁输出率”、`reviewable` 状态、人工接受率或全流程完成率混为一谈。

## 八、失败分类与报告

每次失败记录首个可证实偏差及证据，至少区分：`no_candidate`、`patch_format`、`patch_apply`、`wrong_behavior`、`incomplete_fix`、`regression`、`scope_violation`、`test_tampering`、`clarification_needed`、`timeout_or_budget`、`infrastructure`、`oracle_invalid`、`unknown`。基础设施和答案无效可作为运行有效性另行审计，但不能静默删除；Agent 自我解释不能代替执行证据。

正式报告至少包含：

- 数据版本、来源/许可证分布、语言/缺陷类型/仓库分布、划分与近重复审查方法。
- 预注册运行数、实际完成数、无效题/无效运行及逐项理由、模型和工具配置哈希。
- pass@1 主指标、各硬门槛分项、分组结果、置信区间和失败分类。
- 每次生成/重试的成本、Token、耗时、超时与缺失数据覆盖率。
- 逐题机器可读结果索引、隐藏评测器版本和可审计产物哈希；公开报告不暴露私有源码或隐藏答案。
- 结果解释范围：合成/公开/私有授权数据分别统计，不将小样本开发集提升表述为生产效果。

## 九、建议的建集顺序

1. 先选一个语言/测试环境，收集 20–30 个候选真实缺陷，跑通题目准入、隐藏测试隔离和逐题报告；此阶段是流程试点，不作普遍效果结论。
2. 清理无效题和近重复后，按仓库/缺陷族划分 dev、validation、test；test 题由不同于建题者的复核者审核预期行为与隐藏测试。
3. 先冻结数据和 scorer，再跑模型；不要根据冻结 test 结果修测试或提示词。若修正错误，应升级数据集版本并保留旧报告。
4. 正式样本量按希望检测的差异、基线通过率和置信区间宽度确定。若任务数小或置信区间宽，明确称为探索性结果；重复同一题不能替代增加独立缺陷。
5. 扩展到其他语言、真实跨文件仓库、并发/状态缺陷和安全场景时，分别补齐对应运行环境和验收专家，不用单一 Python 纯函数集代表多语言项目。

每题是否有效由基线与参考修复的程序执行证据确认；数据准入审核和 Agent 最终补丁评分由不同产物表示。本文、现有评测器的自检、参考补丁通过数都不是 Agent 成绩本身。
